# Vesktop voice calls in the Caelestia dashboard

Status: implementation in progress. This is the durable source of truth for this project. Preserve this file across context resets and update the checklist with verified results only. No release tag is planned.

## Goal and boundaries

Show a dedicated voice-call view in the full and compact dashboard media widgets when Vesktop is connected to a call. For a guild VC show the guild icon (or fallback), for a private call the remote user's avatar, for a group DM its icon (or fallback). Show call/channel identity and participants, self mute/deafen, per-participant local Discord volume and a Vesktop application-volume control. Retain MPRIS music and its selector when music and a call coexist. Distinguish unavailable, not in call, and connected; do not show a stale call after disconnect or restart.

Do not use Discord user tokens, self-bots, bots to control the local client, or the arRPC Rich Presence socket for voice. Discord output volume inside the app is distinct from PipeWire application-stream volume; implement it only after a separate action/state probe. Support stage channels only after an explicit probe. Prefer a Vencord userplugin built into Vencord; do not fork Vesktop unless its own behavior blocks the supported custom-build or system-Vencord paths.

## Protocol sketch (to validate before freezing)

Current implemented protocol: connect-and-read JSON line, plus allowlisted versioned commands on the same socket, from `$XDG_RUNTIME_DIR/caelestia-voice/vesktop-voice.sock` (0700 parent, 0600 socket), version `1`, `{version, connected, call, self?, participants?}`. The renderer publishes validated full snapshots through Vencord `native.ts`; the native socket sends its latest snapshot then closes. Participant arrays are bounded to 64 guild members; IDs/names/image URLs/flags and optional Discord local volume are validated. Connected snapshots carry a random epoch and a live-verified action capability flag. Guarded `selfMute`, `selfDeaf`, and remote `volume` commands require matching call ID/epoch; acknowledgements wait for observed readback and time out. No subscription stream or native `available` state exists. Same-UID processes are not isolated by socket permissions.

Target command protocol (not yet implemented): add a versioned request/response boundary with bounded frames, allowlisted `setSelfMute`, `setSelfDeafen`, `setParticipantVolume`, call epoch/id and request ID. Do not export tokens or general JS/Node invocation. Re-read state after executing each action.

Render-side store candidates: `SelectedChannelStore.getVoiceChannelId()` cross-checked with RTC; `VoiceStateStore.getVoiceStatesForChannel()` for guilds; `CallStore`/`ChannelRTCStore` for private/group calls; media engine for local volume. The actual action creators, participant semantics and event subscriptions must be verified against the running Discord/Vencord build before promising controls. A disconnect publishes an explicit empty-call snapshot; a failed/stale IPC connection never leaves a call visible indefinitely.
